The Private Clubs API is public and generously rate-limited for standard use. Most integrations — including LLM agents, club-finder applications, and research tools — will never come close to the default limits. This page documents the limits per endpoint, explains what happens when you exceed them, and gives you practical guidance on staying within bounds.

## Limits by Endpoint

| Endpoint | Rate Limit | Notes |
|---|---|---|
| `GET /ai/clubs.json` | 100 requests / min per IP | No auth required |
| `GET /api/clubs` | 100 requests / min per IP | No auth required |
| `POST /api/mcp` | 60 calls / min per MCP session | Session-scoped, not IP-scoped |
| `GET /llms.txt` | No limit | Response cached for 1 hour |
| `GET /llms-full.txt` | No limit | Response cached for 1 hour |
| `GET /ai/context.md` | Not documented — treat conservatively | Response is static summary |
| `GET /openapi.json` | Not documented — treat conservatively | Rarely needs re-fetching |

<Note>
Rate limits apply **per IP address** for the REST endpoints and **per MCP session** for the MCP endpoint. If your service routes all outbound requests through a shared IP (e.g., a NAT gateway or a serverless execution environment), all requests from that IP count toward the same bucket.
</Note>

## HTTP 429 — Too Many Requests

When you exceed the rate limit for an endpoint, the API returns an HTTP **429 Too Many Requests** response. The response body will contain an error message explaining that the limit has been reached.

```json
HTTP/1.1 429 Too Many Requests

{
  "error": "rate_limit_exceeded",
  "message": "Too many requests. Please slow down and try again shortly."
}
```

<Warning>
Do not retry immediately after receiving a 429. Implement an **exponential backoff** strategy — wait at least one second before the first retry, and double the wait on each subsequent failure. Hammering the API after a 429 may result in a longer cooldown period.
</Warning>

### Recommended backoff pattern

<CodeGroup>
```python Python
import time, urllib.request, json

def fetch_with_backoff(url, max_retries=5):
    delay = 1
    for attempt in range(max_retries):
        try:
            with urllib.request.urlopen(url) as r:
                if r.status == 200:
                    return json.loads(r.read())
        except urllib.error.HTTPError as e:
            if e.code == 429:
                print(f"Rate limited. Retrying in {delay}s...")
                time.sleep(delay)
                delay *= 2
            else:
                raise
    raise Exception("Max retries exceeded")
```

```javascript JavaScript
async function fetchWithBackoff(url, maxRetries = 5) {
  let delay = 1000;
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const res = await fetch(url);
    if (res.ok) return res.json();
    if (res.status === 429) {
      console.log(`Rate limited. Retrying in ${delay}ms...`);
      await new Promise(r => setTimeout(r, delay));
      delay *= 2;
    } else {
      throw new Error(`HTTP ${res.status}`);
    }
  }
  throw new Error("Max retries exceeded");
}
```
</CodeGroup>

## Best Practices to Avoid Rate Limits

### Cache responses locally

Club data — especially fee information, amenity lists, and founded years — changes infrequently. Cache responses in your application for at least a few minutes, and cache the `/ai/context.md`, `/llms.txt`, and `/llms-full.txt` files for up to an hour (they are already cached at the CDN level for that duration).

### Use pagination efficiently

`/ai/clubs.json` supports up to 500 results per page and `/api/clubs` supports up to 100. If you are fetching a large dataset, use the maximum `limit` parameter to reduce the total number of requests needed.

```bash
# Fetch up to 500 clubs in a single request instead of five requests of 100
curl "https://www.theprivateclubs.com/ai/clubs.json?state=California&limit=500"
```

### Filter before paginating

Apply `type` and `state` filters to narrow the result set before paginating. A filtered request for `type=golf&state=Texas` may return 50 clubs in a single page — far more efficient than fetching all clubs and filtering client-side.

### Avoid redundant requests in LLM loops

If you are building an LLM agent that calls the API in a reasoning loop, store the results in the context window or a short-lived cache between turns. Do not re-fetch the same query on every model invocation.

<Tip>
For the `/llms-full.txt` file, consider fetching it once at agent startup and passing the content directly into the system prompt. This gives your LLM comprehensive TPC context without making per-request API calls.
</Tip>
